Problem statement

The work being automated

Every alert costs an analyst the same four questions.

Who owns this host? Has this address appeared before? Is this the user's own VPN egress? Was there an MFA push?

The queue length isn't the pain. Re-deriving the same context, from scratch, per alert is the pain.

The second problem, which nobody writes about

No leaderboard tells you which local model can do this.

  • Benchmarks measure reasoning, coding, trivia — not "does it escalate benign Windows logons"
  • The failures are per alert class, and they invert between models
  • Nothing published tells you what a model costs in RAM at the context you need

So we had to measure it ourselves. That measurement is most of this talk.

Hypothesis

The bet — three predictions, scored at the end

Constrain the model. Don't scale it.

A 12B model inside a deterministic state graph — one narrow, schema-constrained question at a time. The model never picks a tool, never chooses the next step, never sees a running transcript.

P1 · It can do the job

A model this small can find real attacks and clear the false-positive control.

P2 · The harness is the safety

What makes it safe to use is the pipeline around the model, not the model.

P3 · Freedom makes it worse

Every added degree of freedom — parameters, reasoning budget, free text — costs more than it buys.

Conclusions renders the verdict on all three.

Three things we assumed, and then tested

All three turned out to be wrong.

Bigger is better

Assumed scaling up would improve everything.

More reasoning is better

Assumed a higher effort setting was a free upgrade.

A screening run predicts the real one

Assumed a cheap n=4 pass would rank models correctly.

Results and Learnings pay these off

Each was refuted by measurement, and the reasoning one was refuted in the dangerous direction.

The key metric — learn it once

Benign escalation: a harmless alert marked HIGH.

The test set has 60 normal, harmless alerts per model. The model gives each a severity. A harmless alert marked high or critical is a false alarm a human must investigate. We count them.

low correct medium still acceptable high / critical escalated — a false alarm

Even the winner escalates 28 of 60. Nothing here is a quiet tool yet — alert fatigue is the problem a SOC buys this for, and an agent that adds false alarms is worse than no agent.

Consequence for this talk

The demo is pre-recorded or cut away from. That is a measured conclusion, not a staging preference.

And plan for the slowest run, not the average

A demo is sized by its worst case.

The safety net, measured across all 426 deep reports

The self-check deletes every risky action it catches.

1,517Claims marked “not supported by evidence”
24% vs 16%Risky share of marked claims vs of all selections
0/300Marked risky actions reaching a final report
67Reports where every action was deleted — a safe default is inserted

The model never writes its own uncertainty notes — the pipeline computes them, re-checks every claim in a fresh call, and deletes what fails. When it deletes everything, “escalate to a human” remains.

Closing line

A 12B model on a laptop is safe to use — not because the model can be trusted, but because the pipeline never trusts it. The distance between “ask a human” and “block Gmail” is the pipeline.

And when the safety net itself fails

The self-check timed out on a live run — and the report said so.

17 Aug, the encoded-PowerShell needle. Draft-A selected 13 recommended actions, so the self-check had 13 claims to audit. It exceeded the 120-second timeout and failed.

1failed_calls recorded on the report
13Claims the audit never finished
0Unaudited drafts shipped as complete

The pipeline does not trust the model. It also does not trust itself to have succeeded.

The designed path, not a defect

The failure is written into the timeline, counted in llm_usage, and named in the report’s uncertainty notes. A step that did not run cannot be mistaken for a step that found nothing.

KV cache, not weights, decides what fits on your laptop.

And the default will surprise you

Ollama sizes KV from the model's default context. qwen3.6:27b is 36.5 GB at default and 16 GB at num_ctx=8192. Invisible on a 128 GB Studio. Decisive on a laptop.

Learning 2, the sequel · gated 17 Aug

A generation of architecture work bought zero extra context.

The KV saving is real and large. The base footprint grew just enough to absorb all of it — and it generates at 51 chars/s against 99.

“Newer” is not a scalar. This is a real trade of generation speed for memory efficiency, and on a memory-constrained device the trade cancelled out.

Learning 3 · the measurement one

Every footprint we published was 7.7% too heavy.

ollama ps prints decimal GB. The parser multiplied by 1024³. Every number in the project was wrong by the same constant.

Why it survived

It cleared a full gate, a 16-configuration sweep and two writeups — because a uniform multiplier reorders nothing. Every ranking was still correct. It eliminated one model for the wrong reason.

It surfaced only because a different number looked impossible: a 120B model reporting a KV cost of exactly 0.0 MB/1K, flat across three rungs.

Chase the implausible reading. The systematic error is underneath it.

Learning 4 · the one we caused ourselves

We instrumented every call. It taught us two things.

Useful — the token count is not a cost metric

One run: 20,843 characters of reasoning against 500 reported completion_tokens. A 42× gap. The self-check call alone reported 163 tokens against 6,655 characters of reasoning trace.

completion_tokens counts structured output only. It is never a throughput or cost figure.

Uncomfortable — the logs moved

Capturing the verbatim prompt puts full_log into every report JSON and every database row — not just the alert’s own raw_json.

A report can now leak alert content even if the alert record itself is handled carefully.

Needs a data-handling decision before real SIEM data

Instrumentation is a data-flow change. We added observability to see inside the pipeline, and widened the blast radius of every stored report in the same commit.

What we'd tell you to do

Four things, all measured.

  • Constrain before you scale. The harness carries the structure; extra model capacity mostly buys room to argue away the grounded answer.
  • Use low reasoning effort wherever the model honours it — and verify it honours it by counting reasoning characters, not by checking the request didn't error.
  • Size by KV at your real context, not by download size. Bake num_ctx into a Modelfile variant; per-request doesn't survive.
  • Measure on your own alert classes. Failures cluster, and clusters invert between models. A leaderboard position does not transfer.

All three predictions held. And we name the one we didn't measure.

The unmeasured corner, named

Nobody ran the endpoint of P3 — a big model in a free-form agent loop, end to end. Every measured step toward freedom made results worse; the endpoint itself is inferred, not measured. That baseline is honest future work.
