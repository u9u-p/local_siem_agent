**Critical finding — `gemma4:12b-mlx` does NOT honor Ollama's JSON-schema-constrained output, even on the trivial `{answer: str}` schema.** Re-ran the same live suite with `LLM_MODEL=gemma4:12b-mlx`: `test_live_generate_structured_returns_valid_object` **failed** (`LLMClientError("validation_failed")`, after both the initial attempt and the retry). Diagnosed with a raw HTTP probe against `/v1/chat/completions` with an explicit `response_format: {"type": "json_schema", ..., "strict": true}` body: the model still returned markdown-wrapped content — literally `'json```json\n{\n  "answer": "ok"\n}\n```'` (the stray leading `json` plus triple-backtick fences make it invalid JSON from position 0) — despite the request explicitly asking for strict schema-constrained JSON. A plain unconstrained `chat.completions.create()` call against the same model produced the identical markdown-fenced content, confirming the model is simply ignoring `response_format` entirely rather than Ollama failing to pass it through.

This means CLAUDE.md §6's stated reason for choosing Ollama — "native JSON-schema-constrained output" — is **not a property of Ollama itself, it's model-dependent**, and at least this one model (an MLX-backend model, `qwen3.5:9b`/`qwen3.6:27b`/`gpt-oss:20b` are all GGUF) doesn't support it at all through Ollama's OpenAI-compat layer. The retry-once mechanism provides zero protection here, since the failure is deterministic/systematic (the model doesn't know how to comply, not occasionally noisy) — this is exactly risk #2 below's "unreliably correct" scenario, except worse: it's *never* correct for this model, not unreliably so. **Practical implication: `LLM_MODEL` is not a drop-in swap.** Before ever changing the configured model away from `qwen3.5:9b`, a candidate model must first be smoke-tested against `generate_structured()` with a trivial schema — this project has no fallback path today for a model that can't produce constrained JSON at all (it would just degrade every single report to `NEEDS_HUMAN_REVIEW` via safe-fallback, silently, for every alert). Worth considering whether a future task should add a "does this model actually support structured output" check distinct from `model_available()` (which only checks the model is *pulled*, not that it's *usable* for this project's core mechanism).

**Post-4b real-model probe (before starting 4c):** ran three one-off `generate_structured()` calls against `qwen3.5:9b` with schemas shaped like real future steps (not the live suite's toy `{answer: str}`) — a flat schema (the actual `app.schemas.RiskAssessment`), a multi-enum schema shaped like the Correlate step, and a `list[SubModel]` schema shaped like Self-Check. All three resolved risk #1 and risk #3 below: **the model produced correct, well-reasoned, schema-conforming output on every attempt**, including on the specific nested-list shape CLAUDE.md's real `Report`/Self-Check schemas need. This is genuinely good news for 4c/4d's prompt design. However, it surfaced a new, more concrete version of risk #5: **each call took 55–103 seconds** (qwen3.5 performs internal "thinking" before responding, per its Ollama `capabilities` listing — `["vision","completion","tools","thinking"]`). At ~80s/call average, CLAUDE.md's "6–7 calls per alert stays practical" assumption (§4.2 rule 6) would mean roughly **8–9 minutes per alert** — this needs to be measured against real alert volume expectations and, if too slow, needs an explicit decision in Phase 4c (e.g. suppressing/limiting the model's thinking budget per call, if Ollama exposes that knob for this model) before prompt design proceeds on the assumption that latency is a non-issue.

## Known Risks & Foreseeable Problems

Standing section, organized by phase — add to this whenever a real risk, gap, or development note surfaces (during implementation, review, or later analysis), not just when a phase completes. Unlike "Notes carried forward" below (cross-phase conventions and lessons), this section tracks phase-specific things that could still go wrong, ranked within each phase by how much damage they'd do if unnoticed, not just by likelihood.

### Phase 4a (LLMClient / OllamaClient)

1. ~~The whole premise is still empirically unvalidated against the real target model.~~ **Validated, see the post-4b probe note above** — three realistic schemas (flat, multi-enum, nested `list[SubModel]`) all produced correct, schema-conforming output against real `qwen3.5:9b`. Not yet tried: the full `Report` schema itself, or a 30–50-item MITRE closed-list pick specifically.
2. **Retry-once assumes occasional noise, not systematic weakness.** If `qwen3.5:9b` is *unreliably* correct on some schema shape (not just occasionally wrong), retry-once fails twice every time, and that step's "safe fallback" becomes the normal outcome rather than the exception — silently degrading every report with nothing erroring loudly enough to notice. Still open — the probe only ran each schema once per shape, not enough runs to assess reliability, only capability. **Item 9 below is the confirmed, worse version of this risk** — not "unreliable," but a model that *never* complies.
3. ~~Ollama's structured-output engine has a known limitation CLAUDE.md's real schemas are likely to hit.~~ **Partially validated** — the `list[SubModel]` probe (Self-Check-shaped) is exactly the "nested schema" case this risk warned about, and it worked cleanly. `Report` itself (nesting `list[InvestigationStep]` *and* `list[EnrichmentResult]` together, deeper/wider than the probe) still hasn't been tried.
4. **`health_check()` is reachability-only, not model-aware** — resolved in Phase 4b via `model_available()`, see above. No longer open.
5. **No latency/timeout validation under realistic conditions — now measured, and it's a real concern.** The post-4b probe's three real calls took 55-103s each (~80s average) against `qwen3.5:9b`'s "thinking" mode. At that rate, CLAUDE.md's "6–7 calls per alert stays practical" assumption (§4.2 rule 6) implies **8–9 minutes per alert** — before Phase 4c's actual per-step prompts (likely more tokens of structured context than the probe's short prompts) and before CLAUDE.md §7.1's colocated-Wazuh memory contention are even factored in. This needs an explicit decision (thinking-budget control, a smaller/faster model for some steps, or accepting multi-minute investigations as fine for a POC) before 4c's prompt design proceeds assuming latency is a non-issue.
6. **The `openai` SDK's exact failure-surfacing behavior is more version-fragile than it looks.** Task 6 had to *empirically discover* that `openai==1.109.1`'s `.parse()` raises `pydantic.ValidationError` directly rather than returning `parsed=None` — undocumented by either Ollama or OpenAI. The `>=1.50,<2` pin is wide enough that a different point release could change this again, silently breaking `_attempt`'s exception handling.
7. **Prompt engineering — the actual hard part — hasn't started.** `LLMClient` is solid plumbing around empty prompts; none of CLAUDE.md §4's real per-step prompts exist yet. A good client wrapped around bad prompts still produces bad structured output.
8. Minor: `LLMClientError.kind` is a bare `str` (not `Literal`/enum) — now 5 values, a typo could silently produce an unrecognized kind. `self._last_raw_content` is mutable instance state, safe only because CLAUDE.md's sequential-processing assumption holds — would become a real bug if anything ever reuses one `OllamaClient` across concurrent calls.
9. **CONFIRMED, highest-severity: "native JSON-schema-constrained output" is model-dependent, not a property of Ollama itself — see the Critical finding above.** `gemma4:12b-mlx` returns markdown-fenced content (`'json```json\n{...}\n```'`) instead of raw JSON even when the request explicitly specifies `response_format: {type: json_schema, strict: true}` — confirmed via a raw HTTP probe that the model, not the transport, is the one ignoring the constraint. This fails deterministically (both the initial attempt and the identical retry), so `generate_structured()` always raises `LLMClientError("validation_failed")` for this model on any schema, trivial or not. `model_available()` cannot catch this — it only confirms the model is *pulled*, not that it's *capable of structured output at all*. If a real deployment ever swaps `LLM_MODEL` to an incompatible model (deliberately or by config mistake), every single alert investigation silently degrades to a stub-shaped `NEEDS_HUMAN_REVIEW` report with none of the real analysis anyone would expect, and nothing in the current codebase flags that the model itself is the problem rather than the alert. Worth a dedicated capability check (a smoke-test schema call at startup, distinct from `model_available()`) before Phase 5 lets an operator point this at an arbitrary configured model.

**Recommended before starting 4b:** pull `qwen3.5:9b` and run one real `generate_structured()` call against a schema shaped like an actual future step (e.g. a rough `RiskAssessment`-sized model). That single test would validate or kill risks #1–#3 at once, instead of discovering them piecemeal while 4b/4c are already mid-build.

### Phase 2b (VirusTotalProvider / multi-type indicators)

1. **Two validator bugs were found and fixed at final review, both on the exact boundary Phase 4c/CLAUDE.md §4.1.1 will lean on hardest.** `DomainIndicator`'s regex used to allow a trailing `\n` (Python's `$` anchors before a trailing newline); `URLIndicator` used to validate a `urlparse()`-sanitized string but store the original, uncleaned one (`urlparse` silently strips `\t`/`\r`/`\n` since Python 3.10 — a validate/store mismatch, not an injection today, but a live one the moment `indicator.value` reaches a header or log line). Both are fixed (`\A`/`\Z` anchors; explicit control-character rejection in `URLIndicator`) and tested — but the *pattern* is worth remembering: CLAUDE.md's "LLM proposes, deterministic code validates" design (§4.1.1) is only as strong as these regexes, and LLM-proposed values are exactly the kind of input (stray whitespace, odd encodings) that finds edges like this. Re-scrutinize `IPIndicator`/`HashIndicator` the same way before Phase 4c starts trusting them with real LLM output.
2. **A per-task review structurally cannot catch "the real class's routing was never exercised end-to-end."** Task 6's registry test used a fake `VirusTotalProvider` double with hardcoded `supported_types`; the integration test only ever exercised IP+FILE_HASH, never DOMAIN/URL through the real class. Nothing failed — every test in the branch stayed green even though two of the three advertised indicator types were unverified against the real provider. Fixed (added a `supported_types` pin on the real class + a DOMAIN end-to-end test), but the lesson generalizes: when a plan's task N introduces a type/branch that task N+2's test coverage assumes without re-touching, budget the final whole-branch review to check "does a test actually import/exercise the real class for every advertised capability," not just "do all tests pass."
3. Minor, deferred (not fixed, tracked here per the standing risk-documentation practice): `VirusTotalProvider._path_for()` silently falls through to the URL branch for any indicator type it doesn't recognize (unreachable via the registry today, since `supported_types` gates what reaches `lookup()`, but `lookup()` itself has no such guard); `score` can read `0.0` on a `SUSPICIOUS` verdict when only `suspicious` (not `malicious`) engines fired, indistinguishable from `CLEAN` to anything ranking by score alone; `virustotal.py` dropped the sibling `abuseipdb.py`'s load-bearing comment explaining why `TimeoutException` must be checked before the broader `RequestError`, and its status-code check order (401→404→429) drifts cosmetically from `abuseipdb.py`'s (401→429→404).
4. **A pre-existing CLAUDE.md §Verification claim doesn't fully hold.** `EnrichmentRegistry.register()` does `DailyRateLimiter(_DAILY_LIMITS[provider.provider_id])`, which `KeyError`s for any provider not pre-listed in `registry.py`'s `_DAILY_LIMITS` dict — so "a third enrichment provider could be added by writing one new class, with zero changes to the Agentic Analyst" (CLAUDE.md's own verification checklist) is true only in the sense that the Agentic Analyst itself needs no changes; `registry.py` still needs one dict entry per new provider. Not blocking, but worth reconciling in CLAUDE.md's Verification section, or fixing by moving the daily limit onto the provider itself (`provider.daily_limit`) if a fourth provider is ever added.
5. VirusTotal's real rate limit is tighter than `DailyRateLimiter` models (~4/min in addition to the ~500/day both providers are checked against) — same accepted simplification as AbuseIPDB, now doubled up across two providers instead of one.

### Phase 4b (Agentic Analyst deterministic pipeline skeleton)

1. **The domain-regex extractor over-extracts more than the "harmless" justification accounts for — needs a Phase 4c design decision, not a silent carryover.** `app/agent/indicator_extraction.py`'s `_DOMAIN_RE` matches any dotted string ending in an all-letter 2-63 char label, so ordinary filenames (`setup.exe`, `invoice.pdf`, `auth.log`, `libc.so`) get extracted as DOMAIN candidates from FIM/process-execution alerts — a large fraction of Wazuh's real output. These then route to `VirusTotalProvider`, consuming its shared 500/day quota (shared across DOMAIN/URL/FILE_HASH) and landing in `Report.enrichment_findings` as misleading "domain: setup.exe — clean" rows. The plan's "over-extraction is fine, false positives resolve harmlessly to UNKNOWN/CLEAN" justification was written before considering a real rate-limited provider and a real analyst-facing report together — it doesn't hold once both are in play. Also see `ROADMAP.md`'s Phase 4c note on this. A prior attempt during Task 2 to fix this by adding a file-extension denylist to production code was correctly reverted (it was also incomplete — didn't cover `.html`/`.php`/`.log`/etc.) in favor of leaving the plan's original regex and correcting the test's expected counts — the fix belongs in a deliberate 4c design decision, not a task-level patch.
2. **The persisted copy of a `Report` has 8 timeline entries, not 9 — it's always missing its own `finalize_and_persist` entry.** `_step_finalize_and_persist` now calls `save_report()` before that step's own `InvestigationStep` exists (needed to close two uncaught-exception paths found at final review — see below), so the SQLite row never includes the finalize step describing its own outcome; only the in-memory `Report` object `investigate()` returns to its caller has all 9. This is a known, disclosed trade-off (there's no `AlertStore.update_report()` to patch the timeline back in after the fact), not an oversight — revisit when Phase 5 builds report-browsing/persistence-update functionality, since that's the first point where anyone actually reads a persisted report's timeline back.
3. **Two uncaught-exception paths out of `investigate()` were found and fixed at final review, both invisible to per-task review because they depend on composition that doesn't exist yet.** `_step_enrich` used to let `EnrichmentRegistry.enrich()`'s bare `ValueError` (raised when no provider is registered for an indicator's type) crash the whole investigation — the per-task reviewer rated this low-risk since production always registers both providers today, but the final reviewer correctly noted there's no composition root yet (Phase 5's job), and a future "register a provider only if its API key is configured" wiring would make a partial registry the *normal* state on a host with only one enrichment API key set. Similarly, `_step_finalize_and_persist` used to let `SQLiteAlertStore`'s `AlertNotFoundError` crash `investigate()` if the alert wasn't already persisted via `save_raw_alert()` first — an implicit precondition all three end-to-end tests satisfied but nothing enforced. Both now degrade gracefully instead of crashing; see risk #2 above for the trade-off this fix introduced.
4. Minor, deferred: `_assemble_report` hardcodes `model_name="qwen3.5:9b"` rather than reading it from `Settings.llm_model`/the injected `LLMClient` — a run against a differently-configured model would misstate its own audit metadata; `_step_enrich`'s timeline entry always says `action="completed"` even when every result came back `UNKNOWN`/errored, so the timeline alone doesn't surface enrichment failures the way CLAUDE.md §5 asks (the data is still in `enrichment_findings`, just not summarized in the step's own audit trail — and Phase 4d's `uncertainty_notes` derivation from CLAUDE.md §4.1 step 8 will want this signal); step 4's `AgentContext`/`RuleMetadata` results are gathered but never consumed by anything yet (expected while steps 5-8 are stubs, but nothing will notice if 4c forgets to thread them through); `InvestigationStep.action` is a bare `str`, not an enum, despite now having 4 consistent literal values (`completed`/`skipped`/`degraded`/`stub`) that tests already assert on; the regex extractor only scans `alert.full_log` and top-level string values of `alert.data` — nested `data` (e.g. Windows `data.win.eventdata.*`) and the structured `source_ip`/`destination_ip` fields are never scanned, and `source_ip` is arguably a Wazuh alert's highest-confidence indicator.

## Notes carried forward

- Every subsystem's **final whole-branch review** (not the per-task reviews) has caught at least one Critical/Important bug invisible at task scale — Foundation's datetime-JSON-serialization crash, Enrichment's incomplete exception handling, Integration's bare `IndexError` on Wazuh's normal "not found" response plus a genuine MITRE-array mispairing bug that had been sitting in the design spec/plan itself. Keep budgeting for that final review + one fix round on every phase; don't skip it because per-task reviews were clean.
- `app/schemas.py` and `app/config.py` are shared foundations every later phase extends (Enrichment added `abuseipdb_api_key`, Integration added six `wazuh_*` fields to `Settings`) — expect the Agentic Analyst to do the same rather than inventing a parallel config module.
- Integration established a typed-error convention `LLMClient` now follows a third time: `LLMClientError(kind, message)` in `app/llm/errors.py`, same pattern as `EnrichmentError`/`SIEMConnectorError` — a single class with a `.kind` discriminator, never raising past the module boundary as a raw vendor exception. Kinds: `unreachable | model_not_found | generation_failed | validation_failed | timeout`. Phase 4b/4c/4d should keep using this convention rather than inventing a fourth shape.
- **Process lesson from Phase 4a's Task 9:** an implementer bundled an unauthorized production-code change into a task explicitly scoped as test-only, and silently rewrote an already-approved prior task's test to match. A re-reviewer caught it by explicitly checking "did this task touch files outside its stated scope" — not just correctness. Worth keeping that as a standing check for any test-only task going forward.
- Phase 4a chose the `openai` SDK (pointed at Ollama's OpenAI-compatible endpoint) over Ollama's native API — verified against Ollama's actual documented behavior, not assumed. `OllamaClient` is generically typed (`TypeVar` bound to `BaseModel`) so callers get their concrete Pydantic type back, not the `BaseModel` base class — Phase 4b's steps should follow the same generic pattern when they build their own typed call sites.
- Phase 4b is next — see Roadmap Phase 4a-4d for the full sub-phase breakdown. It needs to resolve the `health_check()` model-availability open item (above) as one of its first decisions.
- Phase 2b confirmed a design audit can eliminate a task entirely: the original plan for a second Enrichment provider assumed `EnrichmentRegistry.enrich()` would need to become `list[EnrichmentResult]`-returning to support multi-provider reconciliation — re-auditing `registry.py` before writing the design spec showed `register()` already loops `provider.supported_types`, so a second, differently-typed provider needed zero registry changes beyond one rate-limit config line. Worth re-auditing existing code against the *actual* requirement before designing a change, not just the requirement as first stated.
- Phase 2b's final review is the first one in this project to find and fix *validator* bugs specifically (see Known Risks above) rather than error-handling/serialization bugs — a new category worth watching for specifically in any future task that adds a Pydantic `field_validator`.
- **Phase 4b: a plan itself can have a bug in its worked-out test expectations, and the fix belongs in the plan/test, not production code.** Task 2's brief specified an exact regex and claimed it would produce "6 candidates, 5 validated" against its own sample text — the controller's manual analysis missed that the same regex also matches a filename (`payload.exe`) embedded in the sample URL. The first implementer attempt silently added an unrequested production-code workaround (a file-extension denylist) to force the brief's incorrect numbers to pass, rather than flagging the discrepancy — caught in task review, reverted, and fixed correctly by restoring the exact brief-specified regex and correcting the test's expected counts instead. The general lesson (a repeat of Phase 4a's Task 9 incident, different shape): when an implementer's fix target is "make this pre-written test pass" rather than "implement this specified behavior," a mismatch between the two should always surface as a question, never get silently resolved by changing whichever side is more convenient to change.
- **Phase 4b: the final whole-branch review caught two uncaught-exception paths a per-task review structurally cannot see, because they depend on composition (multiple providers, an alert already being persisted) that doesn't exist as a single unit until the whole branch is assembled.** Per-task review correctly checked "does this step's code handle the errors it was told to handle," but "is there a code path where a *different* dependency state — no providers registered for a type, an alert not yet saved — reaches this step" is a whole-system question. Keep budgeting a final review pass that asks "trace one exception per external dependency through the full pipeline," not just "did each task's own tests pass."
- Phase 4c is next — see `ROADMAP.md`'s Phase 4 section for the full sub-phase breakdown and the domain-regex over-extraction decision it needs to make explicitly (Known Risks above, Phase 4b #1).
