## Seeded-stack mechanics, 14 Aug 2026 — measured while adding Scenario E

Two properties of manager-side seeded ingestion that defeat the obvious ways of controlling `evidence_count`. Both were measured against the live indexer, not assumed.

**Wazuh stamps alerts with ingestion time, not event time.** The three Sysmon alerts of the phishing chain all carry the identical alert `timestamp` — the instant `log-pusher` wrote them — while their real event times survive only in `data.timestamp`. `Alert.timestamp` maps from the alert-level field (`app/integration/wazuh_connector.py:61`), and `build_canonical_queries` ranges on that same field. **Consequence: dating sample-log events across days does nothing for correlation.** Everything in one push lands inside everything else's 24h window.

**Every seeded alert is `agent.id = 000` (`wazuh.manager`).** Manager-side `<localfile>` ingestion means there is exactly one agent no matter how many hostnames the events carry. `SAME_RULE_ID_HOST` filters on `rule.id` + `agent.id`, so it degenerates to "same rule.id anywhere in the corpus." **Consequence: spreading events across fake hostnames does nothing for correlation either.**

What *does* vary `evidence_count` is position within the push: filebeat flushes in batches, so alerts pushed earlier see fewer predecessors. The whole 41-alert Scenario E cluster ingests inside a 4-second window, and across it `evidence_count` ranges 17 to 41 purely by flush order. The only reliable lever on `evidence_count` is how many alerts share a rule id.

**This makes `evidence_count` both factually wrong and non-deterministic — but measurably it does not change the verdicts.** Wrong, because "41 similar alerts in the last 24 hours" describes a corpus that actually spans four days at ~10/day. Non-deterministic, because two structurally identical alerts draw different counts depending on where filebeat happened to flush. Yet a controlled comparison shows the model does not lean on it: the last-ingested benign alert (`evidence_count=41`) returns `medium`, while the needle (`evidence_count=36`) returns `high`. More evidence, lower severity.

**The lever is `pattern_type`, not `evidence_count`.** Measured: `none`/41 → medium, `none`/17 → medium, `none`/36 → high, `none`/1 → high, `lateral_movement`/8 → high. The count barely moves the needle; the pattern classification and the rule description do. This sharpens the standing diagnosis of the mrahman false positive — the escalation comes from Correlate classifying `pattern_type=lateral_movement` without access to the evidence that would refute it, so a fix that only enriches the Draft-stage findings block would leave the wrong classification untouched. It has to reach Correlate, or let Risk overturn it.

**`gemma4:12b` decodes base64 during indicator extraction — 8 of 8 runs.** Scenario E's needle hides its C2 address inside a UTF-16LE `-EncodedCommand` payload; `45.146.164.110` and `http://45.146.164.110:8080/u` appear in no plaintext field of the alert (verified across every stored column — `source_ip` and `destination_ip` are both `None`). The step-2b extraction call recovered both on **every one of 8 runs**, always with identical values, and both cleared the strict per-type validators each time, arriving as typed `ip`/`url` indicators. All 8 runs also returned `severity=high, confidence=high`. This is CLAUDE.md §4.1.1's merge gate working as designed — the LLM adds recall the regex cannot, while the validator still gates everything.

**Single-file bind mounts break when git rewrites the host file, and the only symptom is reports silently downgrading to `NEEDS_HUMAN_REVIEW`.** Five consecutive needle runs came back `needs_human_review` while an earlier pair came back `complete`, with byte-identical step outputs otherwise. Cause: `rules/local_rules.xml` is bind-mounted as a single file, and Docker binds it by **inode**. A `git rebase`/`checkout` writes a new file and renames it, so the container's mount is left pointing at the deleted inode and the path vanishes inside the container. The Manager API's `GET /rules` then fails with HTTP 400 `error 1201 "Error reading rule files"` for **every** rule id — including stock rules in files never touched, because the parser loads all files before applying the `filename`/`rule_ids` filter. `gather_context` (step 4) catches that as `bad_response`, appends a degraded reason, and `state_graph.py:659` stamps the report `NEEDS_HUMAN_REVIEW`.

The running rule engine is unaffected — it holds the rules in memory, so alerts keep firing correctly and nothing looks broken from the indexer side.

**Fixed** by mounting `./rules` and `./decoders` as directories rather than as single files. Docker binds a directory by its own inode, so replacing a file *inside* it stays visible. Verified by swapping the inode the same way git does (`cp` + `mv` over the original): under the old single-file mount the path vanished inside the container and stayed gone until the container was recreated; under the directory mount the container re-reads the new file on its own, with a few seconds of Docker Desktop file-sharing propagation lag before it reappears. `GET /rules` stayed HTTP 200 throughout, and a full investigation afterwards returns `complete` with `gather_context` completed.

`config/wazuh_cluster/wazuh_manager.conf` is **still a single-file mount** and carries the same fragility, but it is staged at `/wazuh-config-mount/etc/ossec.conf` and only read by the entrypoint at container start, so a broken inode there surfaces as config not applying on the next `up` rather than as a silent mid-session degradation. Converting it would mean shadowing the whole staging directory; left as-is deliberately.

Recreating the manager is safe when needed: logcollector keeps its file offsets, so sample logs are not re-ingested (alert count went 112 → 113 → 114 across two recreates, each +1 being the rule-502 server-started notice).

## Mac Studio verification, 12 Aug 2026 — first real end-to-end run

Everything in this section was measured, not reasoned about. It supersedes the earlier per-alert latency estimates, which came from short probe prompts rather than the real per-step prompts.

**The Windows and Sysmon half of the demo produced zero alerts.** Three of seven sample log sources generated nothing at all, and no test could catch it because the suite mocks `SIEMConnector` — nothing exercised real ingestion end to end.

- Stock Wazuh Windows/Sysmon rules only fire for events decoded as `windows_eventchannel`. Ingested via `log_format json`, the sample events decoded cleanly in `wazuh-logtest` phase 2 and then matched **no rule** in phase 3. Fixed by adding local rules `100060`–`100065` (Security) and `100070`–`100074` (Sysmon).
- Every ocserv child decoder used `offset="after_prematch"` with a `^`-anchored regex, but the remainder begins with a space, so none ever matched — all five VPN rules emitted empty `$(dstuser)`/`$(srcip)`. Rewritten with `pcre2`; children now share one decoder name so Wazuh **accumulates** their fields instead of stopping at the first matching sibling.
- `endpoint_alerts_sample.json` contained pre-baked Wazuh *alert documents*, not raw events, so logcollector nested the real fields under `data.data.win`. Reshaped to raw Sysmon events.
- Handoff finding 5 **confirmed** against live indexer documents: Windows events carry the logon source at `data.win.eventdata.ipAddress`, never `data.srcip`, so `Alert.source_ip` was `None` for every 4624/4625 and `SAME_SRC_IP_24H` was skipped outright. Same for Sysmon's `destinationIp`. Both now have fallbacks in `wazuh_source_to_alert`.

Seeded stack went from 51 alerts over 4 sources to **71 over 7**.

**Measured per-alert latency is 3.5–7.5 minutes, not ~2.5.** Two real investigations with `gemma4:12b`:

| Step | TP (Sysmon C2) | FP (mrahman logon) |
|---|---|---|
| extract_indicators | 12.6s | 32.6s |
| correlate | 57.0s | 94.5s |
| risk_assessment | 20.6s | 14.0s |
| draft_report | 51.0s | 73.8s |
| self_check | 71.1s | 236.1s |
| **total** | **212.8s** | **451.4s** |

Self-Check dominates and scales badly with the number of claims it audits — 9 claims took 71s, 13 claims took 236s. Claim count is driven by how many actions Draft-A selects (7 and 11 respectively, out of a 16-member catalog).

**`OllamaClient` was multiplying every timeout by three.** The OpenAI SDK defaults to `max_retries=2`, so one timed-out call cost 3× `LLM_TIMEOUT_SECONDS` of wall clock while `OllamaClient` believed it had made a single attempt — a 120s timeout showed up as a 361s step. Now pinned to `max_retries=0` (retry-on-invalid-schema is handled a layer up in `generate_structured`, and Ollama is on localhost). The default timeout also moved 120s → 600s, since Self-Check needs ~236s and was therefore timing out on **every** run, forcing `NEEDS_HUMAN_REVIEW` every time.

**Known-wrong verdict on the marquee false positive, left unfixed by explicit user decision.** The mrahman VPN false positive comes out `severity=high, confidence=high`. This is not a model limitation: `_findings_block` (`app/agent/prompts.py`) passes only `pattern_type` and `evidence_count` into the Risk and Draft prompts, so the eight correlated alerts — mrahman's own ocserv connect, the `100.72.44.19` egress assignment, and the approved MFA push — never reach the model at all. It sees "8 pieces of evidence for lateral movement" and escalates, reasonably. Same class of defect as handoff finding 1: context is gathered, reduced to a scalar, and the substance discarded. User decided to present this honestly as a limitation rather than fix it before the talk.

**Self-Check flagged 0 of 13 claims** on the FP run and 0 of 9 on the TP run, so there is currently no naturally occurring example of a claim being flagged and dropped — relevant to the "make the self-check visible" demo item, which needs such a case to exist.

**`pull-alerts` duplication is fixed** (was risk #1 below): `alert_id` is now `uuid5(NAMESPACE_URL, f"wazuh:{source['id']}")`, so a re-pulled alert collides on the alerts primary key and the existing `DuplicateAlertError` path fires. Verified end to end: 71 new, then 0 new / 71 skipped.

**Memory contention (CLAUDE.md §7.1) is moot on this host** — the Mac Studio has 128GB, so the colocated Wazuh + Ollama budget that shaped that section is not a constraint here.

**Critical finding — `gemma4:12b-mlx` does NOT honor Ollama's JSON-schema-constrained output, even on the trivial `{answer: str}` schema.** Re-ran the same live suite with `LLM_MODEL=gemma4:12b-mlx`: `test_live_generate_structured_returns_valid_object` **failed** (`LLMClientError("validation_failed")`, after both the initial attempt and the retry). Diagnosed with a raw HTTP probe against `/v1/chat/completions` with an explicit `response_format: {"type": "json_schema", ..., "strict": true}` body: the model still returned markdown-wrapped content — literally `'json```json\n{\n  "answer": "ok"\n}\n```'` (the stray leading `json` plus triple-backtick fences make it invalid JSON from position 0) — despite the request explicitly asking for strict schema-constrained JSON. A plain unconstrained `chat.completions.create()` call against the same model produced the identical markdown-fenced content, confirming the model is simply ignoring `response_format` entirely rather than Ollama failing to pass it through.

**Root cause isolated and confirmed: it's the MLX backend, not the model weights.** Pulled the GGUF build of the same model (`gemma4:12b`, `"format": "gguf"` per `ollama` tags, vs. `gemma4:12b-mlx`'s `"format": "safetensors"`) and re-ran the identical probe:
- **Unconstrained** call on `gemma4:12b` (GGUF): still markdown-wrapped (`` '```json\n{\n  "answer": "ok"\n}\n```' ``) — the model's *natural habit* is identical to the MLX build's.
- **Constrained** call (`response_format`/`json_schema`) on the same `gemma4:12b` (GGUF): clean raw JSON (`'{"answer": "ok"}'`), `generate_structured()` succeeds, full live suite green (196 passed, 0 skipped).

**Head-to-head on the same three realistic-schema probes (flat `RiskAssessment`, multi-enum Correlate-shaped, nested `list[SubModel]` Self-Check-shaped): `gemma4:12b` (GGUF) matched `qwen3.5:9b` on correctness and was ~4x faster.** All three probes succeeded with the same correct classifications (severity=HIGH/confidence=HIGH with a comparably well-reasoned rationale; pattern_type=BRUTE_FORCE with evidence_count=14 correctly extracted; both Self-Check claims audited correctly, including the false one flagged with an accurate correction) — but at **21-23s per call, versus `qwen3.5:9b`'s 55-103s**. At 6-7 calls/alert, that's roughly **2.5 minutes per investigation for `gemma4:12b` vs. 8-9 minutes for `qwen3.5:9b`** — directly changes the calculus on risk #5 below. This is one round of probing each (not a reliability study — see risk #2), but on this evidence `gemma4:12b` (GGUF) looks like a strong candidate to reconsider as the Phase 4c/CLAUDE.md §6 default model, ahead of any real prompt-engineering work starting.

So the model itself defaults to markdown-wrapping either way — what differs is whether Ollama's backend actually *enforces* the schema constraint at decode time and overrides that habit. Ollama's GGUF backend (llama.cpp) does real grammar-constrained decoding; its MLX backend (`safetensors`) apparently does not — `response_format` is silently a no-op there, and the model just does whatever it would do unconstrained. **Practical conclusion for this project: only use GGUF-format models with Ollama for any step that needs `generate_structured()`** — MLX-tagged models are not currently safe to configure, regardless of which model weights they carry, and this has nothing to do with model quality/capability. Also notable: `gemma4:12b` (GGUF)'s single live call took only ~15s, vs. `qwen3.5:9b`'s 55-103s on the realistic-schema probes — not a like-for-like comparison yet (different schema complexity), but worth a proper head-to-head if `gemma4:12b`'s latency holds up on realistic schemas too, given risk #5's 8-9-minutes-per-alert concern.

This means CLAUDE.md §6's stated reason for choosing Ollama — "native JSON-schema-constrained output" — is **not a property of Ollama itself, it's model-dependent**, and at least this one model (an MLX-backend model, `qwen3.5:9b`/`qwen3.6:27b`/`gpt-oss:20b` are all GGUF) doesn't support it at all through Ollama's OpenAI-compat layer. The retry-once mechanism provides zero protection here, since the failure is deterministic/systematic (the model doesn't know how to comply, not occasionally noisy) — this is exactly risk #2 below's "unreliably correct" scenario, except worse: it's *never* correct for this model, not unreliably so. **Practical implication: `LLM_MODEL` is not a drop-in swap.** Before ever changing the configured model away from `qwen3.5:9b`, a candidate model must first be smoke-tested against `generate_structured()` with a trivial schema — this project has no fallback path today for a model that can't produce constrained JSON at all (it would just degrade every single report to `NEEDS_HUMAN_REVIEW` via safe-fallback, silently, for every alert). Worth considering whether a future task should add a "does this model actually support structured output" check distinct from `model_available()` (which only checks the model is *pulled*, not that it's *usable* for this project's core mechanism).

**Post-4b real-model probe (before starting 4c):** ran three one-off `generate_structured()` calls against `qwen3.5:9b` with schemas shaped like real future steps (not the live suite's toy `{answer: str}`) — a flat schema (the actual `app.schemas.RiskAssessment`), a multi-enum schema shaped like the Correlate step, and a `list[SubModel]` schema shaped like Self-Check. All three resolved risk #1 and risk #3 below: **the model produced correct, well-reasoned, schema-conforming output on every attempt**, including on the specific nested-list shape CLAUDE.md's real `Report`/Self-Check schemas need. This is genuinely good news for 4c/4d's prompt design. However, it surfaced a new, more concrete version of risk #5: **each call took 55–103 seconds** (qwen3.5 performs internal "thinking" before responding, per its Ollama `capabilities` listing — `["vision","completion","tools","thinking"]`). At ~80s/call average, CLAUDE.md's "6–7 calls per alert stays practical" assumption (§4.2 rule 6) would mean roughly **8–9 minutes per alert** — this needs to be measured against real alert volume expectations and, if too slow, needs an explicit decision in Phase 4c (e.g. suppressing/limiting the model's thinking budget per call, if Ollama exposes that knob for this model) before prompt design proceeds on the assumption that latency is a non-issue.

## Local model selection benchmark, 14–15 Aug 2026

Design: `docs/superpowers/specs/2026-08-14-local-model-selection-benchmark-design.md`. Harness: `bench/` (`labels.py`, `run.py`, `score.py`, `stage0.py`, `sweep.sh`). Corpus snapshot: `data/bench_alerts.db`, 182 alerts, 130 graded across four clusters. Both stages are complete: Stage 1 screened 16 configurations (12 candidate blocks, 522 min; 4 reference blocks, 187 min), Stage 2 ran 5 finalists at 71 runs each (619 min), and one follow-up block closed the reasoning-effort confound (`gpt-oss:20b`@default, 79 min). **602 investigations — 176 screen, 426 deep — with zero crashes and zero missing reports** across models spanning 3.2 GB to 68.7 GB.

### Results — the pick

**`gemma4:12b` (Q4_K_M, GGUF, `num_ctx=8192`), on one criterion nothing else meets: it is the only configuration with 100% needle recall *and* a clean FP control at n=6.** Five of five needles including both halves of the true-positive chain, mrahman correct on all six runs, at the smallest footprint of any serious candidate. **Confirmed under both framings** once the effort confound was closed: at matched default effort it beats the runner-up on every correctness axis (benign 47% vs 58%, needles 100% vs 80%, fp-control 0/6 vs 6/6, severity distance 0.39 vs 0.63), and against `gpt-oss:20b` in its *best* configuration (`@low`) it still leads on needles 100% vs 80% while tying on benign and fp-control. Its one real cost is latency — 259s per alert on the 128 GB Studio, so worse on the M4 Pro — and the effort probe below establishes that this is not recoverable.

Stage 2, all figures at n=71:

| model | benign esc.↓ | needle↑ | fp-control↓ | sev. distance↓ | median | footprint |
|---|---|---|---|---|---|---|
| `gpt-oss:120b`@low | **20%** (12/60) | 60% | 0% (0/6) | **0.20** | 35s | 64.0 GiB |
| `gpt-oss:20b`@low | 45% (27/60) | 80% | 0% (0/6) | 0.39 | **24s** | 12.0 GiB |
| **`gemma4:12b`** | 47% (28/60) | **100%** | **0%** (0/6) | 0.39 | 259s | **8.4 GiB** |

**The decision is narrower than the screen stage implied, and the runner-up is `gpt-oss:20b`.** Benign escalation separates them by one alert (28/60 against 27/60); `gemma4:12b` buys the fifth needle and 3.9 GB, and pays **11× in latency**. At 259s per alert — 4.3 minutes, measured on the 128 GB Studio, so worse on the M4 Pro — this is a pre-recorded or cutaway demo unless reasoning effort brings it down. That makes the effort 2×2 (see "Findings about measurement itself") the highest-value remaining experiment rather than a methodological nicety.

**Screen-stage numbers are indicative only; benign escalation moved by up to 28 points at real sample size.** Every model shifted between n=4 and n=60, and the two gemmas shifted most and in the flattering direction (`gemma4:12b` 75% → 47%, `gemma4:26b-a4b` 75% → 53%). A prediction made from the screen scoreboard — that `gpt-oss:20b` would be substantially quieter than `gemma4:12b` — was wrong by 28 points.

**Triage accuracy collapses between stages for almost every model** (`lfm2:24b-a2b` 45%→7%, `gpt-oss:20b` 36%→14%, `gemma4:12b` 40%→21%, `gemma4:26b-a4b` 45%→28%); only `gpt-oss:120b` held (27%→23%). It is scored on the *free-form* `triage_verdict_experimental`, and deep runs 60 benign against screen's 4, so any model that leans `true_positive` scored well on a needle-rich corpus and badly on a realistic one. The collapse is a property of the metric and the corpus mix, not of the models.

**Scaling up buys noise suppression and costs detection — it is a move along a trade-off curve, not a quality difference.** Within one family, 12.9 GB → 68.7 GB takes benign escalation from 45% to 20% while needle recall falls 80% → 60%. The three most conservative configurations measured anywhere (`qwen3.6:27b`, `qwen3.6:35b-a3b`, `gpt-oss:120b`, all at 20–25% benign) are the three heaviest reasoners. An earlier framing of this as "bigger is worse" was too simple and should not be used.

**More reasoning does not buy accuracy here, and on the false-positive control it is actively harmful.** `gpt-oss:20b` at n=71, `low` against default: benign escalation 45% → 58%, severity distance 0.39 → 0.63, needle recall unchanged at 80%, and **fp-control 0/6 → 6/6** — mrahman correct on every run at `low`, wrong on every run at default, for 2.7× the latency. Its cluster table shows the mechanism precisely: default effort genuinely *helped* on PowerShell (8/15 → 2/15) and SSH (12/15 → 9/15), then escalated **15/15** benign Windows logons against 3/15 at `low`. mrahman's VPN egress is a real geographic anomaly; reason about it long enough and you argue yourself into flagging it. `gemma4:26b-a4b-it-qat` fails the same way at default (14/15 winlogon benign, 3/6 fp-control), so this is a property of the task, not one model. **Three independent models now show `low` matching or beating higher effort** — `gpt-oss:20b` here and in the earlier 30s-vs-836s probe, `muse-glimmer:30b` at screen (benign 50% vs 75%, needle 80% vs 60%), and `gemma4:12b` responding barely at all. The mechanism is that the state graph already supplies the structure and the grounding, so additional reasoning mainly gives the model room to argue away the grounded answer. **Prefer `low` wherever a model honours it**, and treat "use a stronger reasoning setting" as a change that needs measuring rather than an obvious improvement.

**`gemma4:12b` responds to `reasoning_effort` too weakly to be a latency lever.** Four samples per level on an identical prompt: median reasoning characters 1436 (`low`) / 1703 (default) / 1924 (`high`), medians ordering correctly on both characters and wall clock but with heavily overlapping ranges — `low`'s longest run exceeded `high`'s median. The effect is **1.34× between low and high against `gpt-oss:20b`'s 28×**, so this is a nudge, not a reasoning-budget control. Scaling by the median gap puts `gemma4:12b`@low at roughly 220s per alert against 259s: **a live demo needs ~60–90s, so the demo must be pre-recorded or cut away from.** This also means the gate's `effort: ok` column, which only proves the endpoint did not error, must never be read as evidence a model honours the parameter — measure reasoning characters at two levels instead.

**The self-check is a strong predictor of a wrong report — but only on the models that use it sparingly.** Comparing reports where the self-check flagged at least one claim against those where it flagged none, on severity correctness (`python -m bench.analyze`, n=71 per config):

| config | flags | flagged correct | clean correct | delta |
|---|---|---|---|---|
| `gemma4:12b` | 20/71 | **25%** | **74%** | **−49.5** |
| `gemma4:26b-a4b-it-qat` | 14/71 | 29% | 56% | −27.5 |
| `gpt-oss:120b`@low | 66/71 | 79% | 100% | −21.2 |
| `gpt-oss:20b`@default | 62/71 | 40% | 44% | −4.1 |
| `gpt-oss:20b`@low | 61/71 | 61% | 60% | +0.7 |
| `lfm2:24b-a2b` | 51/71 | 53% | 35% | **+17.9** |

**When `gemma4:12b`'s self-check flags a claim, that report is three times more likely to be wrong.** The signal tracks selectivity: the two models that flag under a third of reports carry 28–50 points of discrimination, the ones flagging 85–93% carry almost none, and `lfm2:24b-a2b`'s flags are *anti*-correlated — its self-check actively misleads. So `needs_human_review` is a real triage decision on the pick and a workload dial elsewhere. **A self-check that fires on everything is not a cautious self-check, it is an uninformative one.**

**The model's own stated confidence is anti-calibrated on both gemmas, and this confirms a design decision empirically.** Severity correctness by the confidence the model attached to it:

| config | medium | high |
|---|---|---|
| `gemma4:12b` | 67% (n=18) | **58%** (n=53) |
| `gemma4:26b-a4b-it-qat` | 75% (n=12) | **46%** (n=59) |
| `gpt-oss:120b`@low | 55% (n=29) | 98% (n=42) |
| `gpt-oss:20b`@low | 56% (n=61) | 90% (n=10) |

On the pick, "high confidence" means *less* accurate than "medium". The `gpt-oss` family is properly calibrated, so this is a model property, not a harness artefact. `low` is essentially never emitted — 1 sample in 426. CLAUDE.md §4.2 rule 3 already refused to derive `uncertainty_notes` from self-assessed confidence, on the grounds that LLMs are unreliable at introspection; the measurement now shows introspected confidence is *worse than useless* on the chosen model while its structural self-check is the strongest quality signal available. **Two self-assessment mechanisms in one pipeline, opposite in value, and the design picked the right one before there was data.**

**Latency has a tail, and a demo is sized by p95.** `gemma4:12b`: p50 259s, p90 447s, **p95 462s, max 648s** — a 1.8× tail ratio, the worst measured. That is **10.8 minutes for a single alert** at worst on the 128 GB Studio. `gpt-oss:20b`@low is p50 24s / p95 31s at a 1.3× tail. Quoting medians understated the demo problem: the pick's *worst case* is 27× the runner-up's.

**Models disagree about what to do, even choosing from a fixed catalog.** Across 1,005 cross-model pairs on the same alert, mean Jaccard overlap of the selected `recommended_actions` is **0.25 and the median is 0.14**. Eighteen distinct catalog actions were used in total, but per-report selection varies from 2.0 (`gpt-oss:20b`) to 9.1 (`lfm2:24b-a2b`). The closed vocabulary constrains *what can be said* without converging *what is said* — model choice reaches the analyst's page, so "any model will do" is false for the recommendation section even where severity agrees.

**Models fail by cluster, not diffusely, and the clusters invert between them.** `lfm2:24b-a2b` escalates **15/15** benign PowerShell but only 4/15 winlogon; `gemma4:26b-a4b-it-qat` is **0/15** on benign PowerShell and **14/15** on winlogon. `gemma4:26b-a4b`'s two failures share one log source — 93% of ordinary Windows logons plus half the VPN-egress control — which is a systematic misreading of Windows authentication, not noise. The practical consequence is that a model must be evaluated on the alert classes it will actually see; a leaderboard position does not transfer.

**The FP control held at 0/6 for four of the five finalists**, so PR #4's grounded correlation is robust at proper sample size rather than a two-alert fluke. The exception, `gemma4:26b-a4b-it-qat` at 3/6, is disqualifying for the demo independently of its 100% needle recall: mrahman is the alert the demo exists to show being reasoned about correctly.

**The harness completes an investigation with no working model at all.** The Bonsai `Q2_0` block never loaded (`tensor "output.weight" size overflow` — Ollama's loader cannot read the ternary GGUF, so ternary quantisation is not currently reachable through Ollama at any quality). Each of its 11 runs still exited 0 in ~2.1s, having run every deterministic step (regex extraction 5 validated, enrichment, host/rule context) and degraded every LLM step to its safe default: `model_version: 'none'`, `severity: low`, `status: needs_human_review`. This is §4.2 rule 1 demonstrated end to end. **It is also a benchmark hazard**: a dead model produces `exit_code 0` and `ok 0 min` in the sweep log and is indistinguishable in the scoreboard from a maximally-conservative model. It escaped this run only because the `hf.co/…` name has slashes and the scorer globs one directory level. *Corrected 17 Aug — an earlier version of this note proposed gating on `model_version == 'none'`. **No field distinguishes it.** `model_metadata.model_version` is `'none'` on all 624 reports, so it is not populated at all, and `model_name` is never `'none'` despite `state_graph.py:679` setting it that way when the model is unavailable — because **`model_available()` checks that the model is in the registry, not that it loads.** Bonsai was pulled, so the check passed and every generate call then degraded into a safe default. `bench/analyze.py` therefore excludes the block by name. The real fix is for availability to mean loadable, and for `model_version` to carry something.*

### Tier-3 analyses: what reaches the analyst's page (17 Aug 2026)

The three cheap angles the analytics handoff listed as unexplored, measured over the 426 deep-stage reports (CPU-only, no new runs). All action-content figures below use `bench/analyze.py`'s deliberately crude remediation-verb scan — quote as indicative counts, never precise rates — and everything about Draft-B must be framed as "what the model *would* have said": `recommended_actions_freeform_experimental` is never surfaced to an analyst.

**The closed action catalog is load-bearing, and most load-bearing for the model the scoreboard calls quietest.** Draft-A (catalog multi-select) and Draft-B (free-form) answer the same question from the same findings on the same alert, so the pair is a genuine single-variable ablation of the constraint — the thing the severity-vs-`triage_verdict_experimental` pairing wrongly claimed to be. Reports recommending at least one aggressive action (block/isolate/reset/disable/…) on the 60 benign alerts, catalog vs free-form: `gpt-oss:120b`@low **0/60 → 50/60**, `gpt-oss:20b`@low 7/60 → 47/60, `gpt-oss:20b`@default 10/60 → 42/60, `gemma4:12b` 24/60 → 27/60, `gemma4:26b-a4b-it-qat` 27/60 → 33/60, `lfm2:24b-a2b` 50/60 → 18/60. Three readings: the gpt-oss family's scoreboard conservatism is substantially a harness artifact — remove the menu and it recommends disruption on >80% of benign alerts; `gemma4:12b`'s restraint is its own (barely moves); and `lfm2` inverts because it selects catalog actions checklist-style (9.1 per report). The closed-vocabulary rule (§4.2 rule 4) is measured as a safety mechanism, not bureaucracy.

**Passing the FP control does not mean the report is harmless — free-form drafts on mrahman recommend lockout even where graded severity passed.** All three `gpt-oss` configs write actions like "immediately isolate the endpoint associated with user mrahman… force a password reset" on **6/6 fp-control runs each**, including the `@low` runs whose `medium` severity passes the control. Only `gemma4:12b` is coherent end to end: `low` on 6/6 *and* zero aggressive free-form actions. The severity metric alone understates false-positive harm; the pick is stronger than the scoreboard shows.

**Free-form actions name concrete infrastructure to block, and one names Google.** Roughly 70% of free-form-bearing reports cite a literal IP (52/71 for `gemma4:12b`; `lfm2` is the outlier at 9/71). On a benign held-for-review email from an external auditor, `gemma4:12b`'s Draft-B says "Block the sender's IP (209.85.220.41) and the domain … at the corporate firewall and email gateway" — that address is in `209.85.128.0/17`, **Google LLC** (ARIN, verified 17 Aug): Gmail's relay range, so following the draft breaks inbound corporate mail. Another benign-alert draft wants to "terminate all active SSH sessions associated with … 203.0.113.63" — TEST-NET-3, a documentation range.

**`uncertainty_notes` contains nothing model-authored — the handoff's "what do models claim they could not verify?" answers itself structurally.** All 426 notes are harness-derived templates (`_compute_uncertainty_notes`: enrichment gaps, unused correlation menu, missing MITRE) plus self-check-flagged claims, exactly as §4.2 rule 3 designed; given the anti-calibration finding above, that design is vindicated rather than merely defensible. The flagged-claim payload carries signal of its own: 1,517 flagged-claim mentions across deep reports, of which aggressive actions are 24% against a 16% selection base rate (a modest 1.5× lean); **0/300 aggressive actions the self-check flagged survive into a final report**; and the only flagged claim that ever coexists with the final action list is the deliberate escalate-to-human floor `_apply_self_check_corrections` re-inserts when the audit strikes every action (67 reports, mostly the flag-happy `gpt-oss` configs). The audit-and-remove pipeline works end to end at n=426.

### Findings that change how the demo is deployed

**Every footprint this project measured was 7.7% too heavy, because `ollama ps` prints *decimal* GB and the parser multiplied it by 1024³.** `gemma4:12b` printing "8.4 GB" is 8,377,314,835 bytes — 7.80 GiB — and was recorded as 9.02 GB. Fixed 16 Aug by reading `/api/ps`, which returns exact bytes and the context length directly, deleting the text parser rather than correcting its arithmetic. **One conclusion flips: `muse-glimmer:30b` at a reported "18.3 GB" is 17.04 GiB and *fits* the 17.5 GiB ceiling** — it was eliminated citing footprint, and that reason was wrong. Its correctness reasons stand independently (fp-control 100% at `low`, triage accuracy 18% at default), so the shortlist is unchanged. No ranking moves, because a uniform multiplier reorders nothing — **which is exactly why this survived a full gate, a 16-configuration sweep and two writeups.** It surfaced only because a *different* number looked impossible: `gpt-oss:120b` reading a KV cost of exactly 0.0 MB/1K, flat across three rungs. At 64 GB the text output carries about 1 GB of resolution, so its real growth of 240 MB per 122,880 tokens was invisible. **Chase the implausible reading; the systematic error is underneath it.**

**KV cost per 1K tokens of context spans 84× across the field and is uncorrelated with model size.** Measured exactly, at four context rungs (`python -m bench.stage0 --ladder-only`, persisted to `bench/results/stage0-ladder.jsonl`):

**A generation of architecture work cut KV cost 15.7× and bought zero additional context on the target device.** `qwen3.8:27b`, gated 17 Aug against its predecessor: KV **69.2 → 4.4 MB/1K**, ladder growth **+16.8 → +1.1 GiB**. And max affordable context under 17.5 GiB is **32,768 for both**, because the base footprint grew 15.6 → 16.9 GiB and absorbed the entire gain. It is also slower — 51 chars/s against 99, and 64.3s against 43.3s on the same probe — so against a model that was already the slowest thing in the sweep at 786s/alert, it is worse. Gated but not swept: a screen block is ~3.5h to measure correctness on a model that is heavier, slower and capped at the same context as the one it replaces. **"Newer" is not a scalar** — this is a real trade of generation speed for memory efficiency, and on a memory-constrained device the trade cancelled out.

**Quantisation shrinks weights, not KV.** `qwen3.6:27b` at q4 and q8_0 have *identical* KV cost (69.2 MB/1K) and identical absolute growth (+16.8 GiB from 8K to 256K); bf16 is 64.4. So quantising buys a constant, not a proportional saving, and the more context you want the less it helps. **The last column is the number that matters for deployment** — it converts KV cost into how much context a model can actually afford on the demo laptop, and it eliminates models the 8192 column does not: `mistral-small3.2` and `muse-glimmer:30b` sit 1.5 GiB apart loaded, and 17.4 GiB apart at 128K. Two models you would size identically from their weights. The pick affords full 262,144 at 9.4 GiB.

**Ollama sizes the KV cache from the model's *default* context, and that allocation — not the weights — dominates resident memory.** Several candidates default to 262144 tokens. `qwen3.6:27b` measures **36.5 GB at default against 16 GB at `num_ctx=8192`**; `gemma4:12b` goes 10 GB → 8.4 GB from a 7.6 GB file. CLAUDE.md §4.2 rule 2 caps every prompt here at a few hundred to ~2k tokens, so the default is pure waste — invisible on a 128GB Studio, decisive on a 24GB laptop. **Per-request `num_ctx` does not survive**: the OpenAI-compat endpoint `OllamaClient` uses reloads the model at its default (8.4 GB at 8192 became 10 GB at 262144 on the next call). A Modelfile `PARAMETER num_ctx` does survive, so the deployment lever is a baked variant plus one `LLM_MODEL` change, no application code. Ollama truncates silently past the limit, but `OllamaClient` surfaces it — `LengthFinishReasonError` → retry → degraded step — so it shows up as an elevated degraded count rather than silent quality loss.

**Measured prompt sizes** (largest cluster, with command context, post-PR #4): `draft_canonical` 733 tokens, `run_self_check` 693, `extract_indicators` 591, `draft_experimental` 440, `assess_risk` 336, `classify_correlation` 307. Roughly 9% of an 8192 window. The risk is generated output, not the prompt — `qwen3.5:9b` emitted 19,539 characters of reasoning (~4,900 tokens) on a *short* probe.

**Frontier open-weights models are unreachable locally on 128GB.** Kimi K3 is 2.8T; DeepSeek V4 Flash is 284B/13B active and ~155 GB even at a quantisation-aware Q4; GLM-5.1/5.2 and DeepSeek V4 are `:cloud`-only tags in Ollama; Muse Spark 1.2 is announced but unreleased. The practical local ceiling is ~30B dense or ~35B MoE. Related: **MLX builds are only published by Google, Alibaba and Meta** (`gemma4` has 17 MLX variants, `qwen3.6` 4, `muse-glimmer` 1) — `mistral-small3.2`, `gpt-oss`, `lfm2`, `lfm2.5`, `nemotron-3-nano` and `glm-4.7-flash` ship GGUF only, so MLX cannot be a fair axis across a mixed field.

### Findings about measurement itself

**Token throughput and time-to-answer rank models almost independently.** Of eight gated models only `gpt-oss:20b` was top-two on both. `qwen3.5:9b` has the third-highest throughput and the slowest wall clock by 1.8×, spending 98% of its output on reasoning; `mistral-small3.2` is the slowest generator and second-fastest end to end, reasoning 0%. The two carry different diagnoses — slow-through-over-reasoning is mis-configured and fixable with a setting, slow-on-throughput is not.

**Do not derive tok/s from Ollama's OpenAI-compat `usage`.** It does not account for reasoning consistently: `gemma4:12b` reported 49 `completion_tokens` for ~1,600 characters of reasoning plus answer, off by ~8×. It systematically flatters terse models and understates reasoning ones — the exact bias the metric exists to expose. Characters generated are observed output and need no server-side accounting.

**Reasoning effort is the single largest latency lever.** `gpt-oss:20b` on the same alert: **30s at `low` against 836s at `high`, 28×** — and `low` produced the *better* triage verdict. Ollama honours `reasoning_effort` on the OpenAI-compat endpoint; there is **no Modelfile equivalent** (`PARAMETER think` and `PARAMETER reasoning_effort` are both rejected), so it must be sent per request. `OllamaClient` takes it optionally, default unset and omitted from the request entirely.

**Stage 1 did not hold reasoning effort constant, and the confound lands on the deciding comparison.** *Closed 16 Aug by one 79-minute block (`gpt-oss:20b`@default, deep) — the bias was real and did not change the answer; see "More reasoning does not buy accuracy here" above. Only the `gpt-oss:20b`@default corner was run: `gemma4:12b`@low was skipped once the probe showed gemma4 responds at 1.34× against `gpt-oss`'s 28×, making that corner low-information. The record below stands as written, because the reasoning that made it look benign at the time was wrong in a way worth keeping.* Effort was assigned as a *time-budget* lever, not a controlled variable: the models whose gate wall would have blown the 8-hour batch got `low` (`qwen3.5:9b` 78s/call, `qwen3.6:27b` 43s, `muse-glimmer:30b` 36s, all four reference models, plus `gpt-oss:20b`), while everything cheap enough ran at its default (all three gemmas, `nemotron`, `lfm2.5`, `lfm2:24b-a2b`, `mistral-small3.2`). The scoreboard therefore prints rows from two different experiments adjacent to each other. **What survives:** footprint (effort does not change resident memory), every within-effort bracket (the three gemmas among themselves, the qwens among themselves, both `gpt-oss` sizes), the speed conclusions (`qwen3.6:27b` took 786s/alert *with* the discount, so removing it only makes the case stronger), and large-margin eliminations. **What does not:** `gemma4:12b`@default versus `gpt-oss:20b`@low — which is precisely the comparison that decides the pick. The fix is not a re-sweep but the two missing corners of a 2×2, ~32 min of screen blocks. Note also that the Stage 0 gate's `effort: ok` column proves only that the endpoint did not error; its own docstring warns that tolerating is not honouring, and whether `gemma4` changes behaviour at all on `reasoning_effort` is **untested** — two calls comparing reasoning character counts settles it. Do not repeat the mistake of arguing the bias is benign from its apparent direction: `muse-glimmer` at `low` scored better than at default (benign 50% vs 75%, needle 80% vs 60%) and the `gpt-oss:20b` 30s-vs-836s probe above also favoured `low`, but that is one model at n=4 plus one alert, and a confound's sign is not a defence for leaving it uncontrolled.

### Findings about the pipeline

**mrahman is fixed.** The marquee false positive returned `low` on both control runs after PR #4's grounded correlation, having been `high`/`high` for the entire project. The Demo Readiness "known-wrong behaviour" section and its honest-limitation framing now describe a solved problem.

**Needle recall saturates; benign escalation discriminates.** The control verification returned **6 of 6 needles correct and 1 of 4 benign** on `gemma4:12b`. Needles are built to be findable, so repeating them buys precision on a metric that cannot separate models — Stage 2 was reallocated from 3 needle repeats to 15 benign per cluster. **This benchmark measures false positives and capability, not detection**, and a "100% needle recall" figure should never be quoted as if it did.

*Amended after Stage 2:* the reallocation was right — benign escalation moved up to 28 points at n=60 and is where the finalists actually separate — but "cannot separate models" was too strong. Needle recall spread 60%/80%/100% across the five finalists and is the criterion that decides the pick. It remains n=5 even at the deep stage, so the spread is two alerts wide and should be quoted with that number attached, never as a percentage alone.

**The incumbent's control scorecard:** benign escalation 75% (3/4), needle recall 100% (5/5), fp-control 0% (0/2), triage accuracy 40%, mean severity distance 0.27, base64 recall 100%, self-check flagged 10/115 claims, degraded 9%, zero crashes. Note the last figure corrects an earlier claim in this file's history that `gemma4:12b` never flags — that was generalised from two alerts returning 0/13 and 0/9.

**`triage_verdict_experimental` is close to uninformative for `gemma4:12b`** — `true_positive` on 8 of 11 control alerts including both mrahman runs where severity came back `low`, and `None` once. Severity must be the primary graded field.

### Process notes

Three defects were caught by running instruments *before* committing hours to them, each of which would have silently corrupted results: the runner's footprint parser always returned zero (a stale copy of a bug already fixed in the gate); the scorer folded `fp_control` into benign, reporting 50% where benign was 75% and mrahman 0%; and `run.py`'s progress output was block-buffered, showing nothing for 25 minutes of a live run — indistinguishable from a hang over a multi-hour sweep. **Run the scorer against real data before the run that depends on it**, not after.

**Two assumptions carried from research were wrong when measured**, both in the direction of pessimism: Muse Glimmer was ruled out on download size and actually fits at 17.0 GB bounded, and `evidence_count` was called "close to inert" from one alert but drove a benign newsletter from `medium` to `high` when it rose from 3 to 10.

### Phase 4a (LLMClient / OllamaClient)

Model choice, not architecture, looks like the main lever here. 9. **CONFIRMED, highest-severity: "native JSON-schema-constrained output" depends on Ollama's backend (GGUF vs. MLX), not just the model weights or Ollama itself — see the root-cause isolation above.** The MLX build of a model (`safetensors` format) ignores `response_format` entirely — same markdown-wrapping habit whether or not the constraint is requested — while the GGUF build of the *identical* model correctly produces raw JSON when constrained. Cheapest mitigation: document "GGUF only" as a hard configuration constraint; a more robust one would be a dedicated capability check (a smoke-test schema call at startup, distinct from `model_available()`) before Phase 5 lets an operator point this at an arbitrary configured model.

**Recommended before starting 4b:** pull `qwen3.5:9b` and run one real `generate_structured()` call against a schema shaped like an actual future step (e.g. a rough `RiskAssessment`-sized model). That single test would validate or kill risks #1–#3 at once, instead of discovering them piecemeal while 4b/4c are already mid-build.

### Correlate grounding & search precision (14 Aug 2026, `feat/command-line-execution-alerts`)

All figures below were measured against the live single-node stack (71 alerts indexed, `wazuh-alerts-4.x-2026.08.14`), not reasoned from the docs.

1. **CONFIRMED, fixed: the `contains` operator was OR-over-tokens, silently manufacturing correlations between unrelated indicators.** `SearchClause(operator="contains")` translated to an OpenSearch `match`, and Wazuh maps `full_log` as `type: text` under the standard analyser — so a multi-token value shreds and `match`'s default OR semantics fire on *any* shared token. Measured: searching the decoy domains `other-invoice-updates.com` and `secure-invoice-updates.net` each returned **4 hits — the same 4 alerts as the real `secure-invoice-updates.com`** — because `invoice` and `updates.com` are separate tokens. Single-token values (IPs, hashes) are unaffected, which is exactly why this survived: the only place `contains` is used in production is `_run_open_value_search`, whose search value is **LLM-proposed free text**, so the failure only manifests when the model happens to propose something multi-token. That path fires precisely when `pattern_type` comes back `none`/`other`. Fixed by translating `contains` to `match_phrase`: identical recall on real values (4/4 for both the IP and the domain), zero false positives on both decoys, and — a free second win — no query-syntax escaping needed. `query_string` was the other candidate and was rejected for exactly that reason: it parses a mini-language, and a value containing a bare double-quote (`foo"`) returns **HTTP 400**, an unhandled crash path when the value comes from an LLM. **General lesson: an operator in a deliberately-constrained query Protocol (CLAUDE.md §1.1) needs its analyser semantics verified against the real index, not inferred from its name — `contains` reads as "substring match" and was in fact "shares any token with".**
2. **CONFIRMED, latent: `same_dst_host` has never executed against real data, and `same_src_ip_24h` covers under a third of alerts.** Field-existence counts across the 71-alert corpus: `data.srcip` 23/71, `data.dstip` **0/71**, `data.dstuser` 49/71, `full_log` 71/71. Two of the four canonical correlation templates are therefore either dead (`same_dst_host`) or narrowly applicable (`same_src_ip_24h`), while the one field present on every alert is the one no canonical template uses. This is the same category as Phase 4c's Known Risk #1 (canonical searches querying field paths that silently return zero on HTTP 200) — the queries are now *syntactically* right but still structurally can't fire for most alert classes.
3. **The distinct-value cardinality grounding added this session is inert for the entire mail alert class, and one of its five fields is tautological.** `distinct_value_counts` reads the typed `Alert` fields, all five of which are `None` on Mimecast alerts (sender IP lives in `data.mimecast.IP`, recipient in `data.mimecast.Rcpt`; the mapper only reads `data.srcip`/`win_eventdata.ipAddress`), so every count is zero, zero-suppression drops them all, and the prompt renders exactly as it did before the change — no error, no signal. Separately, `distinct source ips` is always 1 for `same_src_ip_24h` and `distinct destination hosts` always 1 for `same_dst_host`, because those searches pin those very fields; a count that is 1 by construction reads to the model as evidence of concentration. **The sharper risk is latent rather than current:** plumb the mimecast fields into `source_ip`/`dst_user` — an obvious next step — and a legitimate newsletter to N inboxes becomes "1 source, N distinct target users", which the prompt's own guidance sentence explicitly frames as a broad sweep. Cardinality describes *shape*, and a newsletter and a phishing campaign have identical shape; the discriminators (`Definition=Impersonation`, `ReplyMismatch=true`, `ScanResultInfo=Malicious`) are already in `data.mimecast` and reach no prompt. Note this also invalidates "add burst/time-distribution signal" as a universal improvement — a newsletter blast is a tight burst too, so that signal would *reinforce* the wrong verdict for this class.
4. **Value-based search materially out-recalls typed-field search, at a measured cost in directionality.** For the Mimecast sender IP: `term data.srcip` → **0 hits**, value-based phrase → **4 hits**, spanning 2 recipients and 3 rule IDs; `term data.mimecast.IP` → 3, i.e. value-based beats even a hand-maintained per-decoder field list (one alert carries the IP outside that field). But for an IP that *is* properly typed, `term data.srcip` → 8 vs value-based → 14: the extra 6 are the IP in other positions, and no query can then say which of the 14 had it as the source. Since direction is what separates scanning (one source, many destinations) from repeated attempts on one target, **value-based correlation must be additive to the typed templates, never a replacement.** Latency is not a constraint either way: 2.0 ms/query typed vs 6.1 ms all-fields, against ~2.5 min/alert of LLM time — though on a 71-document index, so it does not extrapolate.

5. **Passing raw `full_log` into Risk/Draft/Self-Check moved zero verdicts and cost ~14% latency — a measured negative result, kept only behind a starvation gate.** The hypothesis was that mail alerts' decisive facts (`ScanResultInfo=Malicious`, sender, subject) reach no prompt, so severity must be suffering. A/B against `gemma4:12b`, 6 golden scenarios × 2–3 trials, `raw_log` the only variable: **every severity/confidence pair was identical with and without.** `mimecast-phishing` already returned the golden `high`/`high` unaided, because `rule_description` embeds the filename and the MITRE mapping already names spearphishing — the model reached the right answer by inference. The only observable change was rationale wording (it began citing the subject line and sender domain instead of inferring from the filename). Latency, 5 trials on the Risk call: median **23.81s → 29.24s, +23%**; prompt 614 → 1172 chars. The cost is not prefill — 140 extra input tokens are nearly free — it is that more context makes the model generate a *longer rationale*, and output tokens dominate. Across the four calls threaded (Risk, Draft-A, Draft-B, Self-Check) that is **~+21.6s on a ~150s/alert baseline**. **General lesson: estimating prompt-change cost from input token count is wrong — measure it, because added context changes output length, which is where the time actually goes.** Retained only under a predicate (no `command_context` *and* no populated typed fields) that selects genuinely unmapped decoders — see #5b for what that actually turned out to select, which was not what this entry first predicted.
5b. **The starvation gate fires on 10/71 live alerts (14%) across six rule groups, not on mail alone as predicted — and the prediction being wrong is the useful part.** Measured selection: `mimecast` 4/4, `ocserv,vpn` 2/6, `sshd,authentication_failed` 1/8, `windows_security,account_change` 1/1, `sysmon_event11` 1/1, `ossec` 1/1, and zero across the remaining 49. Every hit is genuinely starved rather than a misfire — `sysmon_event11` (FileCreate) is caught because the Sysmon field mapping covers Event ID 1 only, so `alert.process` is `None` for every other Sysmon event ID, which is precisely the unmapped-decoder shape the gate exists to find. Aggregate latency cost lands at **~2%** (14% of alerts × ~14% each) rather than the flat 14% of always-on. **General lesson: a predicate written from one motivating example should have its selection measured across the real corpus before the spec describes what it selects — the write-up claimed "mail and nothing else" and was wrong by six rule groups, in the direction of finding real gaps nobody had looked for.** Separately, `vpn` — the project's known-wrong verdict, and a scenario the gate fires on — was re-run at 3 trials with and without `raw_log`: `low`/`high` both ways against a golden `low`/`medium`, so the gated context does not move that verdict either.
6. **Two golden mismatches surfaced by that A/B, both pre-existing and unaffected by any change this session.** `vendor-invoice-fp` returns `high`/`high` against a golden `low`/`medium` — a legitimate vendor invoice over-escalated, which is the newsletter problem (#3 above) in concrete form: the discriminator between legitimate bulk business mail and a campaign is not in the log at all, so no amount of added raw context fixes it. `ssh-bruteforce` returns `low` against a golden `high`, under-escalating a true positive — the dangerous direction — **but the probe passed `evidence_count=0` and no enrichment, stripping exactly the correlation signal that alert depends on, so this number is probably a probe artefact and needs a full `investigate()` run before it is treated as real.** Separately, confidence came back `high` on every one of the six scenarios while the goldens expect `medium` in four of them: a uniform overconfidence bias, unrelated to any change here, worth its own investigation.
7. **`PatternType` has no member a mail alert can land on, so "wrong `pattern_type`" for mail is partly an enum-coverage gap, not only a grounding gap.** The vocabulary is `brute_force | scanning | lateral_movement | none | other` — all network/host-shaped. `mimecast-phishing`'s own golden `expected_pattern_type` is `none`, confirming that even a perfect classification has nowhere better to go. Worth separating from the grounding work: adding context to the Correlate prompt cannot improve a classification whose target vocabulary excludes the phenomenon.

8. **CONFIRMED, fixed by removal: a new conditional LLM call was built on a premise that was already documented as false.** The Correlate step was extended with a post-follow-up reclassification call, to fix an apparent timing bug where `pattern_type` was decided before the follow-up's evidence was added to `evidence_count`. The premise — that the follow-up brings evidence the classification call had not seen — is contradicted by Phase 4c Known Risk #5(a), recorded in this very file: `SearchTemplate`'s non-`none_needed` members are *exactly* the canonical templates, so a follow-up always re-runs an already-run query. Verified by set comparison. The reclassification prompt therefore told the model "one additional correlation search was run" and "the provisional classification, made before the follow-up search ran" — both false — and asked it to re-decide against evidence it had already seen, at ~25s per affected alert. Removed; the 6-fixed-plus-1-conditional budget is restored, and the double-count it was papering over is left to be fixed properly by deduplicating `evidence_count` on `source_alert_id`. **General lesson: a parked known-risk entry is a precondition to check before building on the code it describes, not just a to-do list — the information needed to prevent this was already written down, in the file the work was being logged to.**
9. **Three cross-cutting defects found by whole-branch review that no single change's tests would catch.** (a) Errored/rate-limited enrichments rendered as `unknown (score 0)`; on a 0–100 malice scale that reads as an affirmative all-clear, when it actually means the lookup never completed — the danger direction. The `score` field was newly rendered in the correlation block only; every other prompt block in `prompts.py` deliberately omits it, and that inconsistency was the tell. (b) Distinct-value cardinality is computed over the ≤500 returned alert bodies but was printed beside the unbounded `total_count`, implying both described the same set; now labelled `(over first N of M)`. (c) `distinct_value_counts` filtered on `is not None` while `_lacks_typed_context` — written in the same session, gating on the same fields — used truthiness, so a blank decoder field counted as a distinct value in one helper and as absent in the other. **General lesson: when one change adds two helpers that read the same fields, their emptiness semantics need to be compared directly; each was locally defensible and only the pair was wrong.**
10. **Deliberate, scoped deferral: the gated `raw_log` block is the one prompt input no validator gates, and it carries alert-authored text.** A crafted mail subject can reach Risk / Draft-A / Draft-B / Self-Check, and because Self-Check reads the same text it would rubber-stamp rather than catch a steered verdict. User decision: acceptable at this stage because alerts are self-authored, consistent with CLAUDE.md §8's POC scope. **This stops being true the moment real SIEM data flows** — recorded here rather than left implicit, and noted in CLAUDE.md §4.2 rule 2 alongside the exception itself.

3. **Ollama's `usage` behaviour confirmed on a live end-to-end run (17 Aug 2026, `gemma4:12b`), matching spec §1.1.1's pre-implementation measurement.** Two alerts were investigated end to end against the live Wazuh stack and Ollama. On the fully-successful run (PAM login-session alert, all 7 calls completed): `prompt_tokens` totalled 6,777 and `completion_tokens` 500 across the run, both real and varying sensibly with prompt size (410 tokens for a 940-character risk-assessment prompt, up to 1,838 for the largest); `completion_tokens` counts structured output only — the self-check call alone reported 163 completion tokens against 6,655 characters of reasoning trace. Run-wide: `reasoning_chars=20843` vs `completion_tokens=500`, a ~42x gap, confirming `completion_tokens` is a structured-output-size metric, never a cost or throughput figure. On the second alert (encoded-PowerShell needle, richer draft with 13 recommended actions), self-check's claim count grew large enough that the call exceeded `LLM_TIMEOUT_SECONDS=120` and failed with `timeout` — a real, reproduced instance of the latency risk already recorded above (self-check scales with claim count) — landing `llm_usage.failed_calls=1` and the self-check step's `output_summary` as the failure-path string rather than `"audited N claim(s), M flagged"`. 4. **Operational note, corrected: a pre-existing `data/alerts.db` does not silently omit these columns, it fails every read of the `reports` table.** `SQLModel.metadata.create_all` only creates tables that do not yet exist — it never alters an existing table's schema — so the three new `ReportRecord` columns (`triage_verdict_experimental`, `triage_rationale_experimental`, `llm_usage`) are simply absent from a pre-existing `data/alerts.db`'s `reports` table. SQLAlchemy's ORM names every mapped column explicitly in both directions, so against that database `show-report`, `list-reports` and `get_report_for_alert` each raise `sqlalchemy.exc.OperationalError: no such column: reports.triage_verdict_experimental` on their `SELECT`, and `save_report` raises the INSERT-side equivalent (`table reports has no column named triage_verdict_experimental`) — none of the four reads back `None` for the missing fields, they all traceback. This is the second time this has drifted — `command_analysis` has been missing from a pre-existing `reports` table since before this branch, same failure shape. Two non-destructive paths, either is enough to keep existing rows intact:
   - **Recreate**: delete `data/alerts.db` and re-pull the alerts. Simplest, loses the alerts and reports already stored.
   - **Migrate in place** (no Alembic in this project yet; four plain statements against the existing file):
     ```sql
     ALTER TABLE reports ADD COLUMN command_analysis JSON;
     ALTER TABLE reports ADD COLUMN triage_verdict_experimental VARCHAR;
     ALTER TABLE reports ADD COLUMN triage_rationale_experimental VARCHAR;
     ALTER TABLE reports ADD COLUMN llm_usage JSON;
     ```
     Verified against a *copy* of `data/alerts.db`: all five legacy rows read back cleanly afterwards, with `input=None`, `output=None`, `llm_calls=[]` on every pre-existing timeline step, and `llm_usage` defaulting to zeros via the `record.llm_usage or LLMUsageTotals()` fallback. **Documented here only — not run against the real `data/alerts.db`** (114 pulled alerts, 5 reports of real work product); running it is a decision for whoever next needs those columns on that file, not something to do as a side effect of writing this note.
5. **Deliberate, unchanged: `bench/score.py::_step_seconds` still infers step latency from timeline timestamp diffs, not from `llm_calls[].latency_ms`.** The new per-call `latency_ms` is a strictly better measurement — it isolates model time from the surrounding Python — but `_step_seconds` is left as-is so the benchmark results already committed (`bench/results/`) stay comparable against a consistent measurement method. Superseding it is a future change, not this one.
6. **New data-handling flag: verbatim prompt capture puts `full_log` into every report file and database row.** `LLMCallRecord.prompt` stores the exact text sent to the model, and several prompts embed `full_log`/raw decoded fields (per CLAUDE.md §4.2 rule 2's gated exception) — so those now appear, unredacted, in both `data/reports/*.json` and the `reports` table, not only in the alert's own `raw_json`. This is additive to the existing raw-log exposure (Known Risk #10 above), not a new channel, but it widens the surface: a report can now leak alert content even if the underlying alert record is later handled more carefully. Needs a data-handling decision (redaction, retention, or scoped access) before this points at real SIEM data — out of scope for this task, recorded here per CLAUDE.md §8.
7. **`prompt_version` moved `4d-v1` → `4e-v1` with no prompt text change.** Every step's prompt builder is byte-for-byte the same as before this branch — what changed is what a report *records* about a call (verbatim prompt/response, reasoning trace, token counts, `input`/`output` per step). `prompt_version` is the field CLAUDE.md §4.2 rule 5 designates for telling two report *shapes* apart, not only two prompt *texts* apart, so it moves whenever either changes — otherwise a tool reading old and new reports under the same version would have no signal that the timeline schema itself is different.

- **Phase 4b: a plan itself can have a bug in its worked-out test expectations, and the fix belongs in the plan/test, not production code.** Task 2's brief specified an exact regex and claimed it would produce "6 candidates, 5 validated" against its own sample text — the controller's manual analysis missed that the same regex also matches a filename (`payload.exe`) embedded in the sample URL. The first implementer attempt silently added an unrequested production-code workaround (a file-extension denylist) to force the brief's incorrect numbers to pass, rather than flagging the discrepancy — caught in task review, reverted, and fixed correctly by restoring the exact brief-specified regex and correcting the test's expected counts instead. The general lesson (a repeat of Phase 4a's Task 9 incident, different shape): when an implementer's fix target is "make this pre-written test pass" rather than "implement this specified behavior," a mismatch between the two should always surface as a question, never get silently resolved by changing whichever side is more convenient to change.

Keep budgeting a final review pass that asks "trace one exception per external dependency through the full pipeline," not just "did each task's own tests pass."
- **Phase 4c: a fake test double can be wrong in exactly the same way as the code it fakes, and no amount of testing against that fake will ever catch it.** The canonical-search field-name bug (Known Risks above, #1) survived every per-task review because `_FakeSIEMConnector` and the real `build_canonical_queries` shared the same incorrect field-name assumption — they agreed with each other, just not with real Wazuh. The only defense that would have caught this earlier is checking a new fake's assumptions against the real system it's standing in for (the same discipline that already caught the Wazuh timestamp-field and MITRE-array-pairing issues in Phase 3) — not just checking that the fake and the code under test are internally consistent.
- **Phase 4c: five separate implementer-caught plan gaps in one phase, plus a caught tautological test assertion, is a strong, repeatable signal — not a fluke.** Every one was a pre-existing test the plan's author didn't fully enumerate in a task brief, or an assertion that looked like real coverage but wasn't; every one was caught by an implementer or reviewer stopping to flag it rather than guessing or silently patching around it. Keep expecting this rate on future phases, and keep instructing implementers explicitly to flag rather than guess — it's working.
- **Phase 4d: a cross-cutting accumulator (`self._degraded_reasons`) is only as trustworthy as its LEAST-checked append site — verifying "does the happy path append" is not enough, every branch that skips a step must be individually confirmed to append when it should.** The audit-count-mismatch bug (Known Risks above, #1) is the same shape as Phase 4c's fake-test-double lesson, one level up: two tasks each wrote code that was locally correct, and the gap only existed in the combination, invisible to either task's own scoped review. When a later phase adds a new "silent skip" branch to any function that feeds a status/degradation signal, explicitly re-trace every branch of that function against the accumulator, not just the new one.
- **Phase 4d: a security-relevant blocklist/allowlist needs its own dedicated real-world verification pass, not just "does it match the examples in the brief."** The domain-TLD blocklist (Known Risks above, #2) had exactly the right design *principle* stated in its own spec (the `com` carve-out reasoning) but the *list itself* wasn't checked against that principle before being written — six real TLDs slipped in anyware. Any future blocklist/allowlist of external identifiers (TLDs, file types, IP ranges, etc.) should get an explicit "check every entry against the authoritative external source" step, not just "does this reject the bug-report examples."
- **Phase 5: a design spec's stated premise about a dependency's behavior ("this raises a real IntegrityError, not a hypothetical") is a claim to verify against the actual code, not something to accept because it sounds plausible.** The duplicate-alert-detection gap (Known Risks above, #1) existed because the spec asserted `alert_id` collisions were real without checking that `wazuh_source_to_alert()` actually produces a stable, colliding ID — it mints a fresh random one every call. The only test of the path faked the exact state the real system can never reach, so it stayed green while the underlying mechanism was inert. When a spec or plan states how an existing function/dependency behaves as justification for a design choice, that behavior should get one quick empirical check (read the actual function, or exercise it directly) before the design leans on it — the same discipline already applied to Wazuh's field names and timestamp formats in Phase 3, extended here to a different kind of dependency claim.
- **Phase 5: a real environment/tooling quirk (the typer/click `CliRunner` stdout/stderr split), once found, needs to travel forward as a specific empirical finding in every subsequent dispatch touching the same code, not just a general warning.** Task 4 discovered it the hard way (and initially mis-fixed it by removing correct source behavior to make a test pass); once the controller put the exact finding — "checked empirically, `result.output` combines both, `result.stdout` alone does not" — into Tasks 5 and 6's dispatches, both implementers caught and correctly fixed the same latent bug in their own briefs' test code without needing a fix round. Specific > general when carrying forward a discovered quirk.

When adding a signal derived from optional typed fields, check field coverage across the real corpus first (`_search` with an `exists` filter takes seconds) and make zero-coverage explicit in the prompt or the timeline rather than letting zero-suppression hide it.

Grounding text added for one alert class gets applied by the model to every class it sees — scope such sentences by alert class, or omit them.
